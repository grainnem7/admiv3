Board Sequencer Improvement Plan

Five reviewers each looked at the Board Sequencer from a different angle and reported about 60 findings. This plan merges them into six phases. Phase 0 makes the 7-minute performance safe. Phases 1–3 make it sound right and make building a performance easy. Phases 4–5 tidy the app and protect it with tests.

The picture

Five things the reviews agree on

The show can fail quietly

A single error freezes the board, the iPad link can drop without anyone noticing, and one oversized message crashes the server. The music keeps playing while the controls stop working, and nothing on screen says so.

Building a piece is hard work

A 7-minute piece takes about 40–70 clicks across three tabs. Scenes are snapshots of whatever is playing live, cannot be edited, and the tools for them sit about 2,600 px down the Loops tab.

During the show there's no overview

The clock is a small chip. The current scene, the next scene and the time to it are not shown anywhere prominent, and Big board hides them. Deaf and hard-of-hearing performers lose the structure of the piece.

The music works against Tim

Loops merge with Tim's counters instead of layering. The band goes silent when loops play. Fill is barely heard. Scenes reset Tim's own Fill and Evolve.

One file does everything

BoardSequencerScreen.tsx is 4,000 lines, with 72 pieces of state, and re-renders on every frame. The performance logic lives inside it, so it is untested and can't resume after a reload.

Phase 0 · before the show

Make the show safe

Each item is small. Together they remove every known way for a live performance to stop, go silent, start wrong or lose saved work.

Done 20 October 2026. All 14 items are built and tested (1,331 tests passing, plus a browser check). Not yet tried on the real rig. One part is deferred: instruments now wait until they have loaded before taking over, but loaded samples are not yet cached, so changing world still downloads them again.

  1. An oversized iPad-link message crashes the whole serverThe relay has no error handler, so any message over 4 KB kills Vite, which also serves the sound, the iPad and saving. QA reproduced it. Add the error handler, a try/catch around messages, and keep the laptop's own state message well under the limit.criticalQArelay.ts
  2. The opening scene never playsA scene at 0:00 is never applied, because the check needs a time after the start. The piece opens in whichever scene was saved last; in the run it was Home, with the band off. On Play, apply the earliest scene.highPerformerQAclock.ts scenesDue
  3. The board can freeze silentlyOne uncaught error stops the frame loop or the draw loop for good, and an unplugged camera just stops sending frames. The music keeps looping, so no one notices. Catch and count errors, keep the loops running, and show a "Camera stopped · Try again" banner when no frame has come for one second.criticalEngineeruseBoardRuntime.ts
  4. Settings only reach the sound while camera frames arriveSound world, band, Fill and Evolve are pushed to the engine from inside the camera loop. If the camera stalls, scene changes and iPad strips are saved but never heard. Apply each setting when it changes, independent of the camera. As a first step, goScene should apply every setting directly.criticalEngineer
  5. Run the show from a build, not the dev serverDuring a show, the dev server can reload the page if any file is saved, which would end the piece. Add npm run show (build, then preview with LAN access, which already carries the iPad link and the disk copy) and make it the only way to run a performance.highEngineerS
  6. Cancelling an automatic ending doesn't workWith "At the time", Cancel the ending is undone a quarter of a second later. Remember that the automatic ending has fired.highQA
  7. Endings run late, clip, or fight tempo changesThe ending begins up to a pass late, so the piece runs over its length. The final chord is cut off about a third of the way through its ring. A tempo change during the fade or slow-down breaks it. A length shorter than the ending ends the piece at once. Fixes: add a pass to the lead time, delay the stop until the sound has ended, hold the tempo during an ending, and warn when the length is too short.highQATester
  8. One press of Space, or one brush of a pad, can wreck the pieceSpace or ■ Stop resets the clock with no confirmation. Next scene wraps from the last scene back to the first. Delete scene has no undo. While the clock runs, make Stop need a second press, stop Next at the last scene, and add an undo for Delete.highUXEngineer
  9. Loops say "playing" when nothing isAfter Stop or the end of the piece, slots still say "▶ playing" on the laptop and the iPad, and they start again on the next Play. When stopped, show "ready" or clear them. After the piece ends, reset to the first scene.mediumTesterPerformer
  10. Saved work can be lost
    • Two tabs open at once can write one player's settings over another player's loops.
    • If a restore fails, saving stays off for the rest of the session.
    • A 13th scene disappears on reload.
    • The laptop copy accepts writes from any web page, and accepts older or empty data.
    Fixes: keep the active player in memory, add a second-tab warning, catch restore failures and roll back, cap scenes at 12, check the request's origin, and reject older or empty writes.    highQA
  11. Every iPad strip move saves everything, many times a secondDragging a strip saves every player's loops tens of times a second. That competes with the sound scheduler, which only looks 100 ms ahead. Throttle saves to about twice a second, save immediately when the page is closed, and show "not saved" if a save fails.mediumEngineerQA
  12. The iPad link fails silentlyA sleeping iPad leaves a dead connection that still reads "connected". A late disconnect can reset the laptop to "waiting". The code is only remembered after "New code" is pressed, so a reload breaks pairing. The panel can show "connected" and "can't reach" at the same time. Add a heartbeat with a "lost" warning, guard against stale disconnects, save the code on first use, and show one clear connection status.highEngineerQAPerformerTester
  13. The laptop board still shows camera warnings"Camera error: Not supported", "Change camera" and "Find the board first" all appear in laptop mode, and nothing says which board is in use. Hide the camera warnings, show a clear "Board: Camera | Laptop" switch, and clean out laptop counters that fall off the grid or whose colour is deleted. "Save board here" also lags half a second behind a click.mediumUXTesterQA
  14. Changing sound mid-piece can drop notesChanging sound world or Evolve swaps in sampled instruments before their samples load, so their notes are silent for a moment. Load first, then crossfade, and keep loaded samples in a cache. This matters at every scene change.highEngineerM
Phase 1 · before the show

Make the music serve Tim

These come mostly from the test performer, who ran the piece and read the session log. Today the instrument quietly works against the player.

Items 1–7 done 20 October 2026: loops layer (Tim takes bass, chords and drums over while his counter is down), the band answers Tim only, scenes leave his moved strips alone (a switch), loops are drawn on the board, Fill is weighted so 30% is heard, Evolve changes one colour at a time, and the pass length is shown. The default grid is now 8×8, one counter per square, as you chose; existing players keep their own grid, which can be changed in the Groove tab. Perform shows the pass length and flags short loops. Item 8 waits until Tim has tried the endings.

  1. Loops should layer, not mergeA red counter of Tim's cuts into the Shine loop's red melody, and a yellow counter rewrites Bed's chords. Give each launched loop its own phrase group, so Tim plays over Bed instead of into it. After Capture, stop the captured counters doubling the loop.highPerformerM
  2. The band should only give way to TimLoops count as "the player's parts", so the band hands them over and is silent for the whole Build section. Only Tim's live counters should take a part from the band.highPerformerS–M
  3. Scenes should set the stage, not take over Tim's controlsAt 3:30 a scene resets Tim's Fill and Evolve under his finger. Each scene should be able to say what it changes, with "leave Tim's strips alone" as the default.mediumPerformerEngineer
  4. Draw the playing loops on the boardLoops are invisible: with Bed playing, the board looks empty. Draw loop notes as outlined counters in the slot's colour, pulsing when they sound. This follows the visual-feedback principle, and lets Tim and the audience see what is sounding.mediumPerformerUX
  5. Fill should be heardAt 30–40%, Fill added only 4–14 notes every 30 seconds, because phrases leave it no space. Let Fill add notes on beats a phrase owns but isn't sounding, scale it to how dense the phrases are, and show "+N added" on the iPad. Confirm Magenta actually loads on the show laptop.mediumPerformer
  6. Evolve should change one colour at a timeAt 50%, every instrument changed at once, about every 43 seconds. Stagger the changes by colour, keep instruments inside the sound world, and set the rate in seconds rather than loops.mediumPerformer
  7. A grid that suits a pieceNew players start on 4 steps, which at 90 BPM is a 2.7-second loop. Default to 8 steps and show "1 pass = 5.3 s" wherever passes are chosen.mediumPerformerS
  8. An ending Tim leadsWhen End piece is pressed, show a "landing" ring on the board, and let the final chord follow the harmony Tim is actually on rather than always the home chord.ideaPerformer
Phase 2 · the big one

The performance builder

The engineer, UX and performer reviews all proposed the same thing from different directions. A performance should be one thing you open, edit and play: one saved document holding the loops, scenes, times and ending, edited on a timeline and played from a dedicated show view.

Built 20 October 2026: Perform is its own tab, opening first, with a timeline, editable scenes in time order (checked as you type), loop pads, a one-line ending summary, Make my plan and a Ready check. A Now / Next strip shows during the piece, on Big board too. The opening scene is in place before the first note, the player's own settings come back when the piece ends, and the clock's decisions are a tested function. Not yet: several pieces per player, "Run from 3:30", resume after a reload. Scenes are still stored as before, with no separate Performance document.

How making a 7-minute piece should feel

  1. Perform → New piece. Choose the length (7:00) and a template, "Arrival · Build · Open · Home" or blank. A 7:00 timeline appears with the four scenes already placed.
  2. Loops shelf: 8 pads along the top. Put counters down (camera or laptop) and press Save to pad, or Draw. Name each one in one field. Saving over a loop asks first.
  3. Click a scene on the timeline. An editor opens beside it: tick which loops play, then set sound world, band, Fill, Evolve and what the scene leaves to Tim. Edits save as you make them. Drag a scene's edge to move its time, which snaps to whole passes.
  4. Ending is the last block on the timeline: style, how many passes, and whether you press End or it ends at the time.
  5. Rehearse: "Preview this scene" and "Run from 3:30".
  6. Ready check: iPad connected and touch seen, backup saved, camera colours OK, no empty loops, Magenta loaded, clock set to start by hand.
  7. Show mode: Big board plus a strip showing Now and Next. The only controls are ⏱ Start, Next, Capture, End and Cancel; Stop needs a second press.
  1. A Performance document, separate from the player's settingsToday a scene overwrites the player's saved tempo, sound and band, so after a rehearsal their "home" settings are whatever the last scene set. Add {name, lengthSec, loops[8], cues[], ending}, with scenes as overrides. A player can own several pieces and export them. Move today's scenes, loops and clock into a default piece when the app loads.highEngineerM
  2. A PerformanceRunner outside the screenMove the clock, scenes, cues, endings, loop launching and iPad actions out of the 4,000-line screen into a plain class that can be tested with fake timers. It can also save its position, so a reload offers "Resume at 3:12". Rehearsing on the laptop board uses exactly the same runner as the show.highEngineerTesterM
  3. Perform as its own place, with a Now / Next stripTake Perform out of the Loops tab. A fixed strip shows a large clock, the current scene, "Next: Build in 0:42", the playing loops as chips, and End. It appears on Play, Big board and Show mode.criticalUXPerformerM
  4. Timeline editor with editable scenesScenes are sorted by time, edited in place, and show every setting they carry. Times are checked as you type ("must be before 7:00"). This replaces "Save scene from now", the free-text time box, and delete-and-save-again.highUXPerformerL
  5. "Make my plan" templateOne button creates the four scenes, their times, the ending and the iPad layout from the current performance plan. The facilitator then only records the five loops with Tim, about 25 clicks instead of about 70.mediumPerformerUXM
  6. Compact loops and simpler clock settingsShow loops as a 4×2 pad grid, or one row per slot with Save, Draw and Clear behind a "⋯" menu. Show disabled reasons as tooltips, not repeated lines. The clock starts by hand by default. Sum up the settings in one line: "7:00 · Final chord over 2 passes · I press End".highUXS–M
  7. Ready-check screenAn automated version of the pre-show checklist: camera running, iPad connected, Magenta loaded (or rules in use), last disk save, backup file saved, loops not empty.mediumEngineerTesterUX
Phase 3

The iPad, made for Tim

Tim has cerebral palsy, plays left-handed, and cannot dwell-hold or shake fast. The iPad currently splits his controls across two pages, and some pads act on any brush of the screen.

Built 20 October 2026: pads chosen per player appear on the Play page (End piece, Next scene, Capture, Stop all, loops). Every pad ignores a resting palm, acts on touch or on lift (per player), and works from a keyboard or switch. The second-tap window is 3, 6 or 10 seconds. Keep only keeps. Next scene can be hidden. The header shows Now / Next and a beat light. Scene pads follow the current scene. Reduced motion is respected and the clock no longer chatters to a screen reader. Checked laptop to iPad in a browser.

  1. One performance page per playerThe facilitator picks the strips and pads Tim needs for this piece, for example Fill, New sound, Keep, Shine and End piece, and they all appear on one screen. No page switching at the 30-second cue.highPerformerUXM
  2. Every pad ignores a resting palm, and can act on liftLoop pads, scene pads, Next scene and the page tabs act on touch-down with no palm check. Check for a palm on every pad, and make "act on touch / act on lift" a per-player setting. Let the facilitator hide Next scene on the iPad.highUX
  3. Adjustable timingThe second-tap window is fixed at 3 seconds. Make it 3, 6 or 10 seconds per player. Make Keep keep, with a separate "Let go", so a repeat tap doesn't undo it.mediumUXPerformer
  4. Show the music on the iPadAdd a header with the scene name, "next: Home at 6:00" and a beat pulse, so there is a visual stand-in for the sound. Page through the scene pads, which currently stop at 4. Respect reduced motion, and stop the screen reader announcing the clock every second.mediumUX
  5. Switch and keyboard accessEvery pad responds to pointer-down only, so switch and keyboard users can't activate them. Add Enter, Space and click activation, and guard setPointerCapture.mediumUXTesterPerformer
Phase 4

Simpler screens and accessibility

  1. Tabs by what you're doingPlay opens on Perform. The tabs are Perform · Sound · Groove · Connections · Session. Everything structural moves to Set up: grid size, pages, lanes, variation, loop bank, box detail and backing song. Hide polyrhythm while phrases are on, or warn that it fights them.mediumUX
  2. Fewer words to learnA "?" glossary next to pass, lane, phrase, band, Fill, Evolve and Hold/Toggle. One name for the three loop systems ("Loop 3 · started by iPad / red counter / pad"). Move Back up and Restore into a file menu.mediumUX
  3. WCAG 2.2 AA fixes
    • Header title contrast about 1.1:1, and grey slider labels about 2.4:1 in light theme.
    • Board grids lack rows and announce gridcells instead of buttons.
    • 100 tab stops on a 10×10 board: use one tab stop with arrow keys.
    • Inputs about 23 px tall: make them full targets.
    • Wrong times and lengths are ignored without saying so.
    • Perform's sections need real headings.
    • Cues and scene changes need larger, longer visual signals.
    highUX
  4. Stop re-rendering the whole screen every frameDraw note pops on the canvas, skip unchanged state, and move live readouts into a small store. This frees the main thread for detection, Magenta and the scheduler, which supports the 20 ms latency goal.highEngineerM
  5. Split the screenSplit it into SetupScreen, PlayScreen and ShowScreen, each reading a small store, with board input behind one interface (camera, laptop, and later iPad). Do it step by step once the runner exists, not all at once. Allow colour changes while playing.mediumEngineerL
Phase 5 · alongside every phase

Tests that guard the show

The building blocks are well tested (the clock, loop launcher and laptop board are fully covered), but the screen that runs the performance has no tests.

  1. Test the performance logicOnce the PerformanceRunner exists, test it with fake timers: a scene fires at its time, each ending style, Stop resets, Cancel restores, Capture takes a free slot, Next stops at the last scene, Delete adjusts the current scene, resume works.TesterEngineer
  2. Test every iPad message, the relay, and savingWrite one table-driven test covering every iPad message: locked strips, loop and scene numbers out of range, Stop all with nothing playing. Test that oversized or malformed messages don't crash the relay and that dead connections are detected. Test the disk copy with a fake fetch and failures. Round-trip two players through backup and restore.TesterQA
  3. Make test noise fail the suiteEvolve throws in 5 test files without failing them, because the test instruments lack setBrightness, and the iPad test lacks React's act setup. Fix both, then fail the suite on "could not change the sound".TesterS
  4. Playwright end-to-end testsAdd @playwright/test; Chromium is already installed. The test server always uses a temporary data folder, so the isolation becomes automatic. A second page plays the iPad, and the clock can be fast-forwarded through 7:00. Eight specs: laptop play, loops persist, launch and Stop all, timed scenes, every ending, player isolation, iPad pairing, backup and restore. Fail on any console error.TesterM
  5. A 5-minute pre-show smoke check on the real rigRun the show build, save a backup off the laptop, sound check, play each loop once, Go through each scene, do a 0:40 run with the real ending, pair the iPad, reload and check everything survives, check the console is clean. This gets added to the performance plan.TesterS
Your call

Decisions before starting

When is the performance?If it's within a few weeks: Phase 0, Phase 1 items 1–4, and the pre-show check, then rehearse. Start the Phase 2 builder after the show.
Should scenes leave Tim's strips alone by default?The performer recommends yes, for Tim's agency. The alternative is that scenes always set Fill and Evolve, as now.
Laptop board for rehearsal only, or on stage as well?If it is also used on stage, it needs the visible-loop drawing and Show mode as much as the camera board does.
Playwright as a dev dependency?Recommended; it replaces the hand-written browser scripts and protects the show flows.
